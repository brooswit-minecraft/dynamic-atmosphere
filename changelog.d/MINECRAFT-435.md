### Changed
- MINECRAFT-435: bounded atmosphere producer scans around Nether/End portal discovery and the portal transfer sink, with no change to gameplay amounts, cadence, RNG semantics, or config. `PortalTransferSink`'s Nether-portal destination search now only queries the destination dimension's known-portal registry for chunks intersecting the existing 128-block search radius, instead of flattening every chunk that dimension has ever recorded a portal in; a single producer-pass call now also reuses an already-validated candidate set across source portals that resolve to the same destination chunk box. Destination resolution is now skipped entirely for a source portal with nothing to transfer, for both the Nether and End legs. The Nether/End portal section scan that `ObsidianPowderGameplay` and `PortalTransferSink` each ran independently on their respective (identically cadenced) producer passes is now a single shared scan per visited chunk per tick (`PortalChunkScanner`), and a `BlockPos` is now only allocated once a block has actually matched, never speculatively for every block a palette-gated section lets through.
- MINECRAFT-435 (review follow-up): the portal section/block scan, the glowstone scan, and the fire/smoke scan each now walk at most a configurable number of palette-gated-in chunk sections per producer call (new `runtime.maxScanSectionsPerCall`, shared `BoundedChunkScanner` engine) instead of scanning every matching section of a visited chunk synchronously; a chunk with more matching sections than the budget allows is fairly requeued (round-robin, behind other pending chunks) and resumes from where it left off on a later call, with no omitted or double-counted blocks across however many calls that takes. The End leg's destination resolution additionally caches its last resolved destination and only falls back to a small bounded registry probe instead of flattening it on every call. A resumable scan's in-progress state is discarded when its chunk unloads or is replaced, so it can never resume against the wrong chunk instance. `AtmosphereMaterialProducer.sampleLoadedChunk` now returns whether this visit's bounded work is done, which the scheduler uses to decide whether to requeue the chunk.
- MINECRAFT-435 (second review follow-up): Obsidian Powder's portal emission and the Nether/End transfer sink's per-chunk source processing are each now their own finite, resumable pass over a chunk's discovered portal positions (new per-chunk pending queues), bounded to `portalTransferSink.maxSourcesPerCall` positions per call and drained to empty -- not merely windowed -- before a new discovery is allowed to begin; a chunk whose pass isn't finished is reported incomplete so its producer visit continues rather than silently deferring the remainder to a whole new scheduled cycle. An O(1) ambient/passive hook sharing a material with one of these resumable hooks (the Obsidian passive sample, the Netherrack ambient sample) is now its own separately-tracked hook, so it rolls exactly once per chunk visit instead of once per resumption call, preserving cadence, emission odds, and the shared RNG sequence. The End registry's bounded lookup (`knownPositionsWindowed`) now walks the registry's own sorted key space directly instead of materializing and sorting every historical key before windowing it, so the traversal cost itself is bounded, not just the returned entry count. A source portal position is now revalidated against the already-loaded source chunk's own live block state immediately before a transfer attempt, so a portal destroyed between when its section was scanned and when its transfer is serviced is never transferred from.
- MINECRAFT-435 (third review follow-up): a chunk instance directly replaced without an intervening unload (`ForgeAtmospherePrototype.ensureImported`'s replacement branch) now also discards every resumable per-chunk state (section cursors, accumulated portals, pending emission/transfer queues, hook-completion flags), matching the existing unload path, so resumed work can never apply against the wrong chunk incarnation. The Nether leg's destination-candidate resolution (registry lookup, live validation, nearest-of-many selection) is now itself a resumable, budget-bounded scan (new `portalTransferSink.maxCandidateOperationsPerCall`, `PortalTransferSink.advanceNetherCandidateScan`) that walks a destination box's chunk entries via a retained live iterator rather than flattening/sorting them, so one densely-populated destination chunk entry can no longer force unbounded live-checks/nearest-comparisons in a single call -- the true nearest candidate is still always found, by keeping a running best-so-far across however many calls a dense box takes to fully examine. The End leg's own candidate validation loop is likewise now bounded by that same per-call budget, short-circuiting on the first eligible hit since it only ever needs "any" destination, not the nearest.
- MINECRAFT-435 (fourth review follow-up): both the Nether and End transfer legs now use peek/pop draining -- a source whose destination resolution hasn't finished this call stays at the front of its pending queue and is retried, instead of being popped and silently dropped once the shared candidate-operation budget runs out. The End leg's own registry scan is now itself resumable and position-bounded (new `PortalTransferSink.advanceEndCandidateScan`, replacing the prior chunk-entry-only bound that still copied every position out of a selected chunk unconditionally) and rotates forward across separate scan attempts so a dense entry's suffix, or anything beyond the first `maxSourcesPerCall` registry chunk entries, is never starved. The Nether leg's per-box discovery (`advanceNetherCandidateScan`) is now anchor-independent -- it accumulates every eligible position in a box rather than a single "nearest so far" -- so two different sources whose anchors happen to share a box correctly reuse the discovery work without ever reusing each other's (potentially different) nearest answer; the anchor-specific nearest selection (new `PortalTransferSink.selectLiveNearest`) happens separately per source and revalidates its chosen winner immediately before transfer, falling back to the next-nearest if the winner has gone stale (destroyed/unloaded) since it was discovered, so a farther but currently valid exit is never hidden by a nearer one that merely used to be valid.
