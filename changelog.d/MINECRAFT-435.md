### Changed
- MINECRAFT-435: bounded atmosphere producer scans around Nether/End portal discovery and the portal transfer sink, with no change to gameplay amounts, cadence, RNG semantics, or config. `PortalTransferSink`'s Nether-portal destination search now only queries the destination dimension's known-portal registry for chunks intersecting the existing 128-block search radius, instead of flattening every chunk that dimension has ever recorded a portal in; a single producer-pass call now also reuses an already-validated candidate set across source portals that resolve to the same destination chunk box. Destination resolution is now skipped entirely for a source portal with nothing to transfer, for both the Nether and End legs. The Nether/End portal section scan that `ObsidianPowderGameplay` and `PortalTransferSink` each ran independently on their respective (identically cadenced) producer passes is now a single shared scan per visited chunk per tick (`PortalChunkScanner`), and a `BlockPos` is now only allocated once a block has actually matched, never speculatively for every block a palette-gated section lets through.
- MINECRAFT-435 (review follow-up): the portal section/block scan, the glowstone scan, and the fire/smoke scan each now walk at most a configurable number of palette-gated-in chunk sections per producer call (new `runtime.maxScanSectionsPerCall`, shared `BoundedChunkScanner` engine) instead of scanning every matching section of a visited chunk synchronously; a chunk with more matching sections than the budget allows is fairly requeued (round-robin, behind other pending chunks) and resumes from where it left off on a later call, with no omitted or double-counted blocks across however many calls that takes. The End leg's destination resolution additionally caches its last resolved destination and only falls back to a small bounded registry probe instead of flattening it on every call. A resumable scan's in-progress state is discarded when its chunk unloads or is replaced, so it can never resume against the wrong chunk instance. `AtmosphereMaterialProducer.sampleLoadedChunk` now returns whether this visit's bounded work is done, which the scheduler uses to decide whether to requeue the chunk.
- MINECRAFT-435 (second review follow-up): Obsidian Powder's portal emission and the Nether/End transfer sink's per-chunk source processing are each now their own finite, resumable pass over a chunk's discovered portal positions (new per-chunk pending queues), bounded to `portalTransferSink.maxSourcesPerCall` positions per call and drained to empty -- not merely windowed -- before a new discovery is allowed to begin; a chunk whose pass isn't finished is reported incomplete so its producer visit continues rather than silently deferring the remainder to a whole new scheduled cycle. An O(1) ambient/passive hook sharing a material with one of these resumable hooks (the Obsidian passive sample, the Netherrack ambient sample) is now its own separately-tracked hook, so it rolls exactly once per chunk visit instead of once per resumption call, preserving cadence, emission odds, and the shared RNG sequence. The End registry's bounded lookup (`knownPositionsWindowed`) now walks the registry's own sorted key space directly instead of materializing and sorting every historical key before windowing it, so the traversal cost itself is bounded, not just the returned entry count. A source portal position is now revalidated against the already-loaded source chunk's own live block state immediately before a transfer attempt, so a portal destroyed between when its section was scanned and when its transfer is serviced is never transferred from.
- MINECRAFT-435 (third review follow-up): a chunk instance directly replaced without an intervening unload (`ForgeAtmospherePrototype.ensureImported`'s replacement branch) now also discards every resumable per-chunk state (section cursors, accumulated portals, pending emission/transfer queues, hook-completion flags), matching the existing unload path, so resumed work can never apply against the wrong chunk incarnation. The Nether leg's destination-candidate resolution (registry lookup, live validation, nearest-of-many selection) is now itself a resumable, budget-bounded scan (new `portalTransferSink.maxCandidateOperationsPerCall`, `PortalTransferSink.advanceNetherCandidateScan`) that walks a destination box's chunk entries via a retained live iterator rather than flattening/sorting them, so one densely-populated destination chunk entry can no longer force unbounded live-checks/nearest-comparisons in a single call -- the true nearest candidate is still always found, by keeping a running best-so-far across however many calls a dense box takes to fully examine. The End leg's own candidate validation loop is likewise now bounded by that same per-call budget, short-circuiting on the first eligible hit since it only ever needs "any" destination, not the nearest.
- MINECRAFT-435 (fourth review follow-up): both the Nether and End transfer legs now use peek/pop draining -- a source whose destination resolution hasn't finished this call stays at the front of its pending queue and is retried, instead of being popped and silently dropped once the shared candidate-operation budget runs out. The End leg's own registry scan is now itself resumable and position-bounded (new `PortalTransferSink.advanceEndCandidateScan`, replacing the prior chunk-entry-only bound that still copied every position out of a selected chunk unconditionally) and rotates forward across separate scan attempts so a dense entry's suffix, or anything beyond the first `maxSourcesPerCall` registry chunk entries, is never starved. The Nether leg's per-box discovery (`advanceNetherCandidateScan`) is now anchor-independent -- it accumulates every eligible position in a box rather than a single "nearest so far" -- so two different sources whose anchors happen to share a box correctly reuse the discovery work without ever reusing each other's (potentially different) nearest answer.
- MINECRAFT-435 (fifth review follow-up): the Nether leg's anchor-specific nearest SELECTION (previously a single unbounded, un-budgeted pass per source, worst-case quadratic if several nearer candidates turned out stale) is now itself its own resumable, budget-bounded scan (`PortalTransferSink.advanceNetherSelection`) over the shared discovery pool -- a monotonic nearest-so-far walk that only rechecks live eligibility when a candidate could actually improve on the current best, so the whole selection costs at most one examination per pooled position, resumable across calls for an arbitrarily large pool, and a source whose selection hasn't finished stays pending rather than being serviced early. The discovered pool itself is now reference-counted and kept alive for as long as any in-progress selection still needs it (not just within one call), so several sources -- even across different chunks or ticks -- genuinely share one discovery; releasing it once nothing references it anymore, and on a chunk's own pending-work cleanup for its still-queued sources, prevents it from leaking. The End leg's registry scan previously treated its per-call chunk-entry window as the definitive end of the search (missing a valid destination sitting just beyond that window and incorrectly reporting a scan as fully exhausted when it had only examined a prefix); it is now a genuine full-registry search spread resumably across however many calls that takes, with the per-call entry count purely a yield point, never a verdict -- detected via wraparound back to the scan attempt's own starting entry, not an arbitrary partial count.
- MINECRAFT-435 (sixth review follow-up): the Nether leg's retained selection winner -- possibly chosen several calls ago and never revisited since -- now gets one final live revalidation (new `PortalTransferSink.finalizeNetherSelection`, itself budget-bounded and resumable) immediately before it's actually used; if it has gone stale in the meantime, the selection restarts over the shared pool instead of transferring to a destination no longer there, so the next-nearest genuinely live candidate is still found. Every point where a finished resumable scan hands its result set off to its consumer (`PortalChunkScanner`'s completed section/block scan, Obsidian Powder's per-chunk portal-emission queue, the transfer sink's own per-chunk pending-transfer queues, and its known-portal registry update) now passes the scan's own result set/iterator through directly instead of defensively copying it into a new collection, so completing an arbitrarily densely-populated scan can no longer itself cost an unbounded synchronous copy in one call. The End leg's full-registry-search completion check no longer depends on remembering a single starting chunk key to detect a wraparound -- which could never fire again, starving the scan forever, if that exact entry were removed from the registry mid-scan (e.g. its only portal destroyed) -- and instead tracks every chunk key visited so far, completing once that count reaches the registry's current size or an already-visited key recurs, which stays correct regardless of such changes.
- MINECRAFT-435 (seventh review follow-up): the Nether leg's final live revalidation check (`PortalTransferSink.finalizeNetherSelection`) now actually spends the shared candidate budget for the check itself, not just for the restart it may trigger -- a call with no budget left retains the still-unconfirmed winner and retries the check on a later call instead of checking it for free. Chunk invalidation (`PortalTransferSink.clearPendingWork`) no longer walks a chunk's whole pending Nether queue to release in-progress selection state; since that queue is always drained head-first, only its front element can ever have any (new pure `PortalTransferSink.abandonFrontOnly`), so the rest -- however many sources are still queued -- is now dropped in O(1) instead of walked one-by-one.
- MINECRAFT-435 (eighth review follow-up): a Nether source's in-progress selection (and its shared discovery pool's reference count) is no longer leaked when that source is handled by one of `transferNetherPortal`'s "nothing more to do" early returns (its portal destroyed, its gas emptied, its dimension no longer eligible, or its destination level unloaded) -- each of those paths now abandons any already-paused selection for that exact source first, the same cleanup `clearPendingWork`'s O(1) front-only optimization already relies on being correct. Disabling throughput mid-pass (`drainPending`'s `throughput <= 0` branch) now routes through `clearPendingWork` itself instead of clearing both queues directly, so it gets the same front-selection release rather than leaking it too.
- MINECRAFT-435 (ninth review follow-up): the End leg's full-registry-search completion check no longer also treats `visitedChunkKeys.size() >= registry.size()` as proof of a completed pass -- comparing a historical visited-key count against the registry's current size can coincidentally match well before every still-remaining key has actually been examined (e.g. two entries visited, one of them since removed, leaving a never-examined third entry that happens to bring the shrunk registry back down to the same size), silently omitting a valid destination. Completion is now detected purely by the cursor genuinely revisiting an already-visited key, which has no such false-positive case.
