bump: patch

### Changed
- MINECRAFT-436: per-player atmosphere/smoke/material network sync is now paced under an explicit, configurable total per-player operation budget (`runtime.maxSyncOperationsPerPlayerPerTick`, default 4096 chunk/cell operations, shared across all 11 sync channels -- the main grid, smoke, and each of the nine materials -- not granted independently to each) instead of sending an entire full-resync snapshot's batches in the single tick that generated them. Which channel is served first rotates every sync tick, so no channel is permanently starved by channels ahead of it.
- A snapshot too large to fit the shared budget in one tick is now delivered as a bounded, fair, atomic continuation across several ticks: queued batches that exceed the remaining budget are split (preserving `reset` only on the first piece and `snapshotEnd` only on the last) so the configured cap is actually enforced rather than bypassed on an oversized first batch; a player is still guaranteed at least one op of progress per tick even when a single indivisible unit alone exceeds the whole budget. A genuine dimension or view-distance change always supersedes any still-undelivered batches of an earlier, incomplete snapshot immediately, even mid-drain -- but the *periodic* full-resync trigger is only ever honored once the previous generation has fully drained, so it can no longer repeatedly discard its own still-in-flight snapshot before completion. A fresh plan is only ever queued once the prior generation is fully delivered (or a genuine change interrupts it), which bounds pending state to at most one generation's worth of batches regardless of elapsed ticks or how fast the live view changes -- it no longer grows unboundedly under sustained change.
- Periodic full resyncs (`runtime.fullSnapshotIntervalTicks`) are staggered per player (a stable hash of the player's UUID picks their phase), computed in units the real sync cadence can actually reach (sync-call count, not raw ticks), so every player is reachable regardless of whether the configured interval divides evenly by the sync interval.
- No wire/packet format change: `AtmosphereGridPayload`/`SmokeGridPayload`/`MaterialGridPayload` and their `reset`/`snapshotEnd` semantics are unchanged, only the tick-by-tick pacing of when already-planned batches are sent.
- A player due for a periodic full resync is no longer silently skipped when their channel happens to be busy, or never reached this tick because an earlier channel in rotation order exhausted the shared budget first: the due-ness is now latched per channel and retried every subsequent tick until that channel is actually idle and applies it, so repeated due/busy alignment (or a rotation phase-lock) can no longer prevent a periodic full resync indefinitely.
- Each chunk's visible cell list (with capacity already resolved) is now cached across ticks and reused for every player whose view includes that chunk, for the main grid, smoke, and each material, instead of every overlapping player independently re-reading the grid and recomputing capacity for the same cells every sync tick. A cache entry is only reused when both the chunk's amount-change revision (tracked from the same dirty-chunk detection already used for persistence) and `TerrainFactsCache`'s own per-chunk generation counter (shared by Vapor/Smoke/every material, bumped on any block change that actually affects capacity) match what they were when the entry was built, so amount-only and capacity-only changes are both still always picked up -- freshness and correctness are unchanged from before, only redundant rebuilding across overlapping players and unchanged ticks is eliminated. A chunk replaced by a different `LevelChunk` incarnation at the same coordinate, OR a chunk that unloads and later reloads (including while a busy paced sync channel never got a chance to observe the earlier exit), bumps that chunk's amount-change revision -- never merely clears it back to its implicit default -- in addition to evicting the shared cache entry, so both the shared cache AND every already-subscribed player's own retained planner freshness state detect the change. A fresh incarnation's own terrain generation, and even the revision if simply cleared back to a shared default, can otherwise coincidentally match what a still-subscribed player's own retained entry already has, leaving ordinary sync for that player stale until an unrelated later change or a full reset. The revision counters are therefore never removed (only bumped) for the lifetime of the server, trading a small amount of unbounded-but-practically-small memory growth (one counter per distinct chunk ever unloaded or replaced) for this correctness guarantee; the cache entries themselves (which can hold real cell data) are still evicted normally.
- Ordinary per-player sync planning (`AtmosphereSyncPlanner`/`SmokeSyncPlanner`) now also uses per-chunk revisions directly: a chunk whose amount revision and terrain generation are unchanged since the last sync is skipped entirely during planning -- its cells are never indexed or diffed -- instead of rebuilding and diffing the player's complete visible cell map every sync tick regardless of how much (if any) of it changed. A stationary player with nothing nearby changing now produces no planning work at all beyond a cheap per-chunk revision scan; when exactly one chunk changes, only that chunk's cells are touched. Entered/exited chunk (subscription) handling, tombstones, capacity-only-change detection, batching, and full-reset-on-dimension/view-change semantics are all unchanged.

### Added
- `runtime.maxSyncOperationsPerPlayerPerTick` server config option (default `4096`, range `1`-`1000000`): the shared per-player cap on chunk/cell operations released across all sync channels each sync tick.
- `TerrainFactsCache.generation()`: a per-chunk counter, shared across Vapor/Smoke/every material, bumped on any block change that actually invalidates cached terrain facts (and on `clear()`) -- the cheap "did this chunk's capacity possibly change" signal the cross-tick cell-snapshot cache and the planner's per-chunk skip both gate on.
- `AtmosphereSyncPlanner.planChunks`/`SmokeSyncPlanner.planChunks` (plus `wouldForceResetChunked`): a chunk-revision-aware planning API, independent of the existing `plan`/`wouldForceReset` (which remain fully functional, unchanged, and still covered by their own existing tests).
- `PacedSyncQueue`, with unit and deterministic planner-to-paced-queue-to-client-cache integration coverage for: budget enforcement including splitting an oversized batch, guaranteed per-tick progress, reset-supersedes-stale-queue behavior, delta-after-snapshot ordering, eventual completion of a periodic snapshot despite an aggressively repeated periodic trigger, correct convergence of changes arriving during an unfinished snapshot, immediate supersession on a genuine dimension change mid-drain, bounded pending weight under sustained delta arrival, and disconnect/retain/clear release of queued work.
- Regression coverage proving per-player periodic full-snapshot staggering is reachable under real configured sync/full-resync intervals (including the previously-unreachable-phase case), that cross-channel budget sharing/rotation never lets total consumption exceed the configured cap, that a pending periodic-resync latch survives both a busy channel and a channel never reached this tick, that `TerrainFactsCache.generation()` bumps only on an actual invalidation or `clear()`, that the cross-tick cell-cache algorithm rebuilds exactly when its amount revision or terrain generation changes (including surviving a chunk-incarnation replacement) and otherwise returns the identical cached instance, and that `planChunks` skips an unchanged chunk entirely (proved by feeding it deliberately wrong cell data and asserting it is never observed) while still correctly handling entered/exited chunks, capacity-only changes within a changed chunk, and dimension/view-distance resets. Further coverage composes the shared cache and `planChunks` together end-to-end, proving that merely clearing a chunk's revision back to its implicit default (rather than bumping it) leaves an already-subscribed player's own retained planner state stale after a chunk-incarnation replacement, and that the shipped fix (bumping) does not. A further case proves the fix also covers a plain chunk unload followed by a reload while a player's planner entry was never told about the exit (the channel was busy), not just an in-place incarnation replacement.
